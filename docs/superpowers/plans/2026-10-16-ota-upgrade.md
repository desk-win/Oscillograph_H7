# 双核固件升级（UART -> QSPI -> 内部 Flash A/B + 回滚）实施计划

> **给执行者：** 本计划按里程碑逐条执行，每条都有「怎么验证」。验证不通过不要往下走。
> 步骤用 `- [ ]` 复选框跟踪。
> **权威设计**：[docs/superpowers/specs/2026-10-16-ota-upgrade-design.md](../specs/2026-10-16-ota-upgrade-design.md)
> 设计里那三条铁律（R1 只写非活动副本且跨 bank、R2 运行路径不改选项字节、R3 永远保留一份可用镜像）
> 是每一步的前提；任何实现与它们冲突，先回来改设计而不是硬写代码。

**目标：** 上位机经 UART 把包含 CM7 + CM4 固件的升级包送到设备，CM7 先暂存到外部 QSPI Flash 并做整包 CRC 校验，校验通过后才写内部 Flash（跨 bank 的 A/B 槽），任一核新固件启动失败都能回滚到上一可用版本；全过程可断电。

**技术栈：** STM32H747（CM7 @480 MHz / CM4 @240 MHz）、STM32 HAL、FreeRTOS (CMSIS-RTOS2)、TouchGFX 4.26、QSPI 外部 Flash、CMake + Ninja。

---

## 全局约束

- **构建命令（在仓库根目录）**：CM7 `cmake --build CM7/build`；CM4 `cmake --build CM4/build`；改了 CMakeLists 先 `cmake -S CM7 -B CM7/build -G Ninja` 重新配置（或直接用 `CM7/CMakePresets.json` 里的 `Debug/Release` 预设）。
- **生成代码不要手改**：`CM4/mx-generated.cmake`、`CM7/mx-generated.cmake`、`CM7/cmake/touchgfx/CMakeLists.txt`、`TouchGFX/generated/` 都是生成物。要改配置就改 `.ioc`（用 CubeMX 重新生成）。可以自由改的是两个 `CMakeLists.txt`、`Mylibrary/`、`Common/`、`tools/`，以及 `Core/` 里 `/* USER CODE BEGIN */ ... /* USER CODE END */` 之间的段。
- **文档编码**：本仓库文档与源码注释是 UTF-8；新文件保持 UTF-8。
- **git**：仓库是 git 工作区（分支 `main`）。每个里程碑结束后按需提交，**不要**用 `git reset --hard` / `git checkout --` 丢别人的改动。
- **调试输出**：CM7 用 `uart1_printf()`（USART1）；CM7 的 OTA 相关日志要能被一个编译开关整体关掉（升级流程本身的输出走 OTA 协议帧，不混进去）。
- **共用事实源**：所有分区/槽地址/暂存区偏移只写在 `Common/Inc/ota_layout.h`，链接脚本与工具都从它派生；不允许第二处硬编码。

## 里程碑与任务

### M0 前置门槛实验（不写产品代码，只做实验与记录）

> 这一阶段的输出是一份实测记录（写在 `docs/superpowers/specs/2026-10-16-ota-upgrade-design.md` 的 §12 表格里回填数值）。**M0 不过，后面全部返工。**

- [ ] **T0.1 QSPI 识别**：临时工具函数读 JEDEC ID（`0x9F`）+ 读状态寄存器，打印厂商/容量；UART 打印或 SWD 观察。
  - 验证：容量与手头芯片丝印一致；把 `FlashSize`/`ClockPrescaler` 的最终值记下来（memory-mapped 测试可选）。
- [ ] **T0.2 跨 bank 写**：从 bank1 执行的代码里擦除并编程 bank2 的一个扇区，擦/写期间让 LTDC 继续扫描 + 一个 10 kHz 定时器中断跑着。
  - 验证：无 HardFault/BusFault；中断计数在擦除期间照常递增（或按手册预期地短暂停顿后恢复）；显示不花屏。
- [ ] **T0.3 同 bank RAM 常驻写**：把擦/写函数放 `.RamFunc`（DTCM），关中断，擦写 bank1 的某个扇区。
  - 验证：能正确写回并回读校验；记录「关中断时长」。
- [ ] **T0.4 时间实测**：128 KB 扇区擦除、32 B flash word 编程，各测 100 次取典型/最坏。
  - 验证：数值填入设计 §13 表格；据此校准所有超时参数。
- [ ] **T0.5 坏 word 读取**：在写一个 flash word 的中途断电（或人为只写一半），下次上电读这个 word。
  - 验证：确认触发的是哪种错误（BusFault / ECC 中断）；跑通设计 §8.3 的容错读路径，扫描器能跳过它并取到上一条有效记录。
- [ ] **T0.6 CM4 复位与上电时序**：实验 `RCC_GCR.BOOT_C2` 置 1/清零，观察 CM4 是否重新从选项字节地址启动；另外上电时用 GPIO 翻转观察 CM4 是否在 CM7 之前就执行代码。
  - 验证：得到明确结论并写进设计 §9.4；若「上电即跑」，T0.5 的坏 word 处理必须加上「向量表最后写」的约束并把结论同步到 §7.2。
- [ ] **T0.7 OTA 串口引脚确认**：对照原理图确认 PC6/PC7（USART6）是否引到对外接口。
  - 验证：确定 OTA 用 USART6 还是复用 USART1，并写进 `.ioc` 计划。
- [ ] **T0.8 选项字节迁移演练**：把一个工程样机按设计 §4.2 迁移到新布局（CM4 到 `0x081C_0000`），跑通；再演练一次「改回 `0x0818` 并烧回旧固件」的救援。
  - 验证：两次都能起来；`SYSCFG->UR3` 回读值与预期一致；把命令序列写成脚本存进 `tools/`。

**M0 退出条件**：T0.1-T0.8 全部通过，且设计 §12/§13 的表格已回填实测值。

### M1 分区与构建骨架

- [ ] **T1.1 事实源头文件**：新建 `Common/Inc/ota_layout.h`，定义 BL/槽 A/槽 B/元数据/CM4 A/CM4 B 的地址与大小，以及 `OSC_OTA_SLOT_ADDR[2]`、`OSC_OTA_MAX_IMAGE_LEN`。
  - 验证：`CM7`/`CM4`/BL 三个 target 都能 include 它；加 `_Static_assert` 保证各区域不重叠、32 B 对齐、总和不超 2 MB。
- [ ] **T1.2 链接脚本**：改 `CM7/stm32h747xx_flash_CM7.ld`（slot A 版，FLASH ORIGIN `0x08020000` LENGTH `768K`）、新建 slot B 版（`0x08100000`/`768K`）、改 `CM4/stm32h747xx_flash_CM4.ld`（`0x081C0000`/`128K`）、新建 BL 的 `.ld`（`0x08000000`/`128K`，RAM 只用 DTCM 前 64 KB + 一段 `.RamFunc`）。
  - 验证：三个链接脚本各自能链接出 elf，`arm-none-eabi-nm` 检查 `_estack`/向量表地址落在正确的槽内。
- [ ] **T1.3 BL target**：在 CM7 工程里加一个 `Oscillograph_H7_BL` 可执行目标（自己的源文件列表 + BL 链接脚本），先把「最小 main：点灯 + UART 打印 + while(1)」跑通。
  - 验证：SWD 烧 BL，上电后 LED 闪烁、UART 有输出，**不初始化 LTDC/TouchGFX/SDRAM**。
- [ ] **T1.4 双槽构建**：让 CM7 应用在同一个构建目录里产出 A/B 两个 elf/bin（两个 target 或两个 `-DOTA_SLOT_ID` 的 object library），并在 `post-build` 用 `objcopy` 生成 `.bin`。
  - 验证：`CM7/build` 下同时出现 A/B 两份 bin；两者 `arm-none-eabi-objdump` 的入口地址分别落在 `0x08020000`/`0x08100000`。
- [ ] **T1.5 尺寸守卫**：构建后脚本检查 `size(bin) <=` 槽大小、CM4 `<= 128 KB`、包内总长 `<= 2 MB`，超限直接报错。
  - 验证：人为把 `LENGTH` 改小应导致构建失败（反向测试一次）。

### M2 QSPI 外部 Flash 驱动与暂存区

- [ ] **T2.1 驱动**：新建 `CM7/Mylibrary/{Src,Inc}/qspi_flash.c/h`：JEDEC ID 表（W25Q/XM25Q/GD25Q/IS25LP 等）、读、页写（256 B）、4 KB 扇区擦/64 KB 块擦、写后回读校验、状态寄存器忙等（带超时）。
  - 验证：写 4 KB 随机数据到指定扇区，回读逐字节一致；擦除后全 `0xFF`；反复 100 次无失败。
- [ ] **T2.2 时钟与 DMA**：`.ioc` 里把 QSPI 的 `ClockPrescaler`/`FlashSize` 改成实测可用值，接上 DMA（QUADSPI 请求经 DMAMUX）。
  - 验证：DMA 读 64 KB 与阻塞读结果一致，耗时显著更短；示波器/逻辑分析仪看 CLK 频率与预期一致。
- [ ] **T2.3 暂存区管理**：实现 stage 头读写（含 CRC）、`bytes_written` 记录（每 64 KB 落一次）、Stage A/B 交替选择与 4 KB 对齐擦除。
  - 验证：写 1.2 MB 假数据到 stage 区，中途断电，重新上电后能从记录的偏移续写并校验整区 CRC。
- [ ] **T2.4 （可选）memory-mapped 模式**：为后续资源外置（A3）预留；若要现在就做，必须在 `MPU_Config()` 加 `0x9000_0000` 非缓存只读区域。
  - 验证：读 `0x9000_0000 + N` 与间接读结果一致；不启 memory-mapped 时该条可跳过。

### M3 镜像头 / 升级包 / PC 工具 / CRC 规范落地

- [ ] **T3.1 镜像与包结构**：`Common/{Src,Inc}/ota_image.c/h` 实现镜像头读写与校验、包总头与条目表解析（结构体直接映射 + 显式小端读写，不用 `memcpy` 依赖对齐）。
  - 验证：主机侧构造的样例镜像/包，固件侧解析出的每个字段与主机打印一致（逐字段对拍）。
- [ ] **T3.2 CRC 规范**：一份 `zlib` 兼容 CRC-32（表驱动），固件与 PC 工具共用同一份自检向量（`"123456789"` -> `0xCBF43926`）。
  - 验证：固件自检断言通过；PC 工具 `python -m pytest` 里同一向量的测试通过。
- [ ] **T3.3 PC 工具（打包）**：`tools/otapack.py`：给 bin 加镜像头、算 CRC、按槽填条目、生成 `.ospkg` 与 manifest。
  - 验证：对现有 CM7/CM4 bin 生成包，再跑一遍 `--verify` 自校验通过；manifest 里的长度/CRC 与手工用 `xxd`+CRC 计算一致。
- [ ] **T3.4 PC 工具（协议库）**：`tools/otaprotocol.py`：帧封装/解析、ACK/重传、超时、进度条；先支持串口回环（不用板子）跑通。
  - 验证：单元测试覆盖：正常流、丢一帧后重传、CRC 错的帧被拒、超时重发 3 次后报错。
- [ ] **T3.5 代理测试**：在 PC 上写一个「假设备」脚本（读帧、按协议回 ACK、写文件），上位机工具对它完整下载一个 1.2 MB 包。
  - 验证：下载结果的 CRC 与包一致；人为注入 1% 丢帧仍能完成（靠重传）。

### M4 UART 协议层（设备侧）

- [ ] **T4.1 接收通路**：`.ioc` 加 UART DMA + 空闲中断（IDLE）；RX 环形缓冲放在 MPU 区域 2（`0x3003_0000` 非缓存）；`stm32h7xx_it.c` 的 `USER CODE` 段里补 `USARTx_IRQHandler`/`DMA_IRQHandler`。
  - 验证：PC 以 921600 连续发 1 MB 随机数据，设备侧计数无丢字节（用计数器 + 打印长度比对）。
- [ ] **T4.2 发送通路**：把 `uart1_printf()` 之外的 OTA 发送改成 DMA + 完成中断（或至少不阻塞 200 ms），并加 TX 忙检测。
  - 验证：接收期间发送不丢数据（双向压测 10 分钟无错误）。
- [ ] **T4.3 帧协议**：`CM7/Mylibrary/{Src,Inc}/ota_uart.c/h` 实现 SOF/类型/序号/长度/负载/CRC-32 的收帧与状态机（超时、错误码、会话 ID）。
  - 验证：T3.4 的测试用例能在真板上复现：正常流/丢帧/坏 CRC/超时/长度越界都得到预期错误码，且设备不卡死。
- [ ] **T4.4 续传与压测**：支持 `bytes_written` 续传；跑 30 分钟反复下载。
  - 验证：续传后最终包 CRC 一致；30 分钟压测无一次需要人工干预。

### M5 应用侧 OTA 服务（CM7）

- [ ] **T5.1 任务与内存**：在 `freertos.c` 新增 OTA 任务（1 KB 栈起步）；所有协议/帧/搬运缓冲用静态数组放 D2 非缓存区；确认 heap 够用。
  - 验证：`configTOTAL_HEAP_SIZE` 调整后 `osThreadNew` 成功；跑 1 小时无栈溢出（开 `configCHECK_FOR_STACK_OVERFLOW`）。
- [ ] **T5.2 CM4 隔离与重启**：实现 HSEM3 握手 + 停采集 + `BOOT_C2` 复位 + 重启后重新走 CM7 侧启动握手（把 `main.c` 里的 `Boot_Mode_Sequence_2` 抽成 `OTA_StartCM4()`）。
  - 验证：连续做 50 次「隔离 -> 复位 -> 重启」，CM4 每次都回到采集状态（`m4_status.uptime_ms` 递增），示波器界面正常刷新。
- [ ] **T5.3 写非活动 CM7 槽**：从 QSPI 读镜像、按 32 B flash word 写入另一个槽、回读整槽 CRC 校验；写前做 `SCB_CleanInvalidateDCache`/`SCB_InvalidateICache`。
  - 验证：故意把源数据改一个字节 -> 校验必须失败并报错；正常时 CRC 匹配；写入期间 LCD 不花屏、CM7 不 HardFault。
- [ ] **T5.4 M4 槽编程**：按设计 §7.2 实现「备份刷新 + 写 A + 校验 + 复位 CPU2 + 确认 + 失败回滚」。
  - 验证：正常流程 CM4 版本号更新且 `uptime_ms` 递增；把包里 CM4 镜像故意改坏 -> CM7 在超时内检测不到确认并自动从 B 恢复 A，CM4 回到旧版本。
- [ ] **T5.5 元数据写入**：`Common/Src/ota_meta.c`：追加记录（双半乒乓）、`seq` 递增、写后回读；同 bank 写入走 `.RamFunc` + 关中断。
  - 验证：连续追加 4096 条记录触发一次「换代」（擦另一半区）后仍能读到最新状态；换代过程中断电，两半区至少一个可用。
- [ ] **T5.6 状态机与 UI**：新增 TouchGFX 升级屏：入口（设置屏里一项）、进度（收包百分比 / 校验 / 烧录 / 重启）、错误码、以及「请勿断电」提示；升级期间屏蔽其它操作。
  - 验证：手动走一遍全流程，界面在每一步的状态与实际日志一致；中途取消/失败能回到正常仪器界面并恢复采集。
- [ ] **T5.7 采集恢复**：升级失败/取消后必须把 CM4 采集、`osc_ctrl`/`log_ctrl` 恢复到升级前状态。
  - 验证：升级失败后立刻测波形与逻辑分析仪，功能与升级前一致（对照升级前的截图/数据）。

### M6 CM7 BL

- [ ] **T6.1 最小可用 BL**：读元数据 -> 校验活动槽（头 + 整镜像 CRC）-> 置 VTOR/MSP -> 跳转；跳转前关中断、清 NVIC、DeInit 用过的外设。
  - 验证：烧好三个镜像后上电，BL 能正确跳到活动槽；把活动槽镜像故意改坏，BL 能跳到另一个槽。
- [ ] **T6.2 试用与确认**：BL 跳转前写 `TRIAL(trial = N)`；应用起来后写 `CONFIRMED`；BL 下次启动发现试用次数耗尽且未确认 -> 切回另一槽。
  - 验证：构造「一启动就 HardFault」的新版本 -> 连续 3 次上电后自动回到旧版本（用版本号在界面上确认）。
- [ ] **T6.3 M4 恢复**：BL 启动时若元数据表明 `m4_state != CLEAN`，在跳转应用之前（此时 CPU2 已被按住）从 B 恢复 A 并校验；任一步失败 -> 进救援模式。
  - 验证：人为把 CM4 槽 A 破坏并置元数据为 dirty -> 上电后 A 被恢复、CM4 正常运行。
- [ ] **T6.4 容错读与元数据兜底**：实现设计 §8.3 的 `flash_read_word_safe()` + BusFault 恢复路径，以及「内部日志不可读 -> 读 QSPI 镜像 -> 再不行进救援」的优先级。
  - 验证：用 T0.5 的方法造坏 word，BL 仍能启动到正确槽；把内部日志整个擦坏，BL 用 QSPI 镜像仍能启动。
- [ ] **T6.5 救援模式**：实现最小协议子集（HELLO/ERASE/DATA/VERIFY/INSTALL/REBOOT）+ LED 指示；进入条件按设计 §7.4。
  - 验证：把两个槽都擦坏 -> 上电进救援模式 -> 用 PC 工具重新烧回一个可用版本并正常启动。
- [ ] **T6.6 （可选）BL 显示**：BL 初始化 FMC+LTDC 显示纯色/一行提示，提示正在升级或处于救援模式。
  - 验证：屏幕上能看到提示且不影响跳转（跳转前把 LTDC 关掉或交给应用重新初始化）。

### M7 端到端联调与故障注入

- [ ] **T7.1 正常升级**：从 A 槽在线升级到 B 槽（含 CM4 固件），全程不干预。
  - 验证：升级后版本号变了、功能自测通过、再次升级能回到 A 槽（A/B 来回各 3 次）。
- [ ] **T7.2 断电注入矩阵**：按下面的矩阵逐点执行，每点至少 5 次。
  - 验证：每次上电后都能正常启动（旧版本或新版本），且能再次发起升级；记录失败/异常点并回归修复。
- [ ] **T7.3 回滚路径**：三种回滚都要跑：CM7 新版本崩溃回滚、CM4 新版本不确认回滚、人工回滚（UI 或工具发命令）。

- [ ] **T7.4 长时间与边界**：包长为 0 / 超长 / 条目数越界 / 版本相同 / 板型不符 / ABI 不符，逐个测试。

## 风险登记表

| # | 风险 | 触发条件 | 影响 | 概率 | 对策 | 对应任务 |
|---|---|---|---|---|---|---|
| 1 | 写内部 Flash 期间断电 -> 槽内容残缺 | 写槽/写元数据时掉电 | 该槽不可用 | 中 | 只写非活动副本；写完回读 CRC；元数据双半乒乓；试用+回滚；BL 能从副本恢复 | T5.3/T5.4/T5.5/T6.2/T6.3 |
| 2 | 两个槽同时不可用 -> 砖机 | 连续两次异常（如回滚时又断电） | 设备不可启动 | 低 | R3 铁律；回滚只改元数据；BL 救援模式（UART 收包） | T6.2/T6.5 |
| 3 | 读半写 flash word 触发 BusFault | 元数据记录写一半后掉电 | BL 启动即崩 | 中 | RAM 常驻容错读 + 跳过坏 word；QSPI 元数据镜像兜底；M0 实测 | T0.5/T6.4 |
| 4 | 改 `BOOT_CM4_ADD` 写错 -> CM4 不起 | 迁移步骤出错 | CM4 功能丢失 | 低 | 一次性动作 + 写后回读；SWD 可改回；动手前演练救援 | T0.8 |
| 5 | 同 bank 写入导致系统冻结/取指停摆 | 代码路径写了自己所在 bank | 系统假死、超时失败 | 中 | R1 铁律 + `.RamFunc`；跨 bank 设计；写入期间关中断 | T0.2/T0.3/T5.5 |
| 6 | CM4 正从被写 bank 取指 | 烧 CM4 槽时 CM4 还在跑 | 行为不确定、可能乱写共享区 | 中 | 先隔离 CM4（HSEM 握手 + `BOOT_C2` 复位）再动 bank2 | T5.2/T5.4 |
| 7 | 缓存/ART 读到陈旧 Flash | 写完立刻读回校验或跳转 | 误判校验结果、跳进旧代码 | 中 | 写后清 D/I Cache；CM4 用复位切换；BL 跳转前失效缓存 | T5.3/T6.1 |
| 8 | 向量表地址错误 | VTOR/MSP 设置错，或镜像链接地址与槽不匹配 | 跳转即崩 | 中 | 镜像头校验 `load_addr`；BL 显式置 VTOR/MSP；双槽两套链接脚本各自验证 | T1.2/T2.1/T6.1 |
| 9 | 升级包 CRC 变体不一致 | 工具与固件 CRC 参数不同 | 校验永远失败或漏检 | 中 | 规范固定单一变体 + 自检向量；两侧共用同一份实现 | T3.2 |
| 10 | UART 传输丢帧/干扰 | 线缆、波特率过高、无流控 | 升级失败或写入坏数据 | 高 | 逐帧 CRC + 序号 + ACK/重传 + 会话超时 + 偏移续传；波特率先用保守值 | T4.1/T4.3/T4.4 |
| 11 | QSPI Flash 型号/容量不明或信号完整性差 | 未知芯片、时钟过高 | 暂存数据损坏 | 中 | JEDEC 自动识别；页写后回读校验；提高时钟前先做压力测试；校验失败自动降速重试 | T0.1/T2.1/T2.2 |
| 12 | CM7 镜像超出槽容量 | 功能增长（现有 595 KB / 768 KB） | 构建失败或方案失效 | 中 | 构建期尺寸守卫；中期把 TouchGFX 资源搬到 QSPI（A3） | T1.5 / 方案 A3 |
| 13 | FreeRTOS heap/栈不足 | 32 KB heap 已用约 20 KB | 任务创建失败或运行崩溃 | 中 | OTA 栈给小、缓冲走静态非缓存区；必要时经 `.ioc` 增大 heap；开栈溢出检查 | T5.1 |
| 14 | CM7/CM4 固件不配套 | 只升了一个核或 ABI 改动 | 数值乱跳等隐蔽故障 | 中 | 包内 `abi_ver` 三方一致校验；安装时拒绝不匹配；运行时界面明确报错 | T3.1/T5.4 / 设计 §9.3 |
| 15 | 升级期间看门狗/中断干扰 | 将来启用 IWDG 或新增高频中断 | 擦写中途复位 | 低 | 预留 `OTA_WDG_Kick()`；擦写期间临界区设计 + 关中断策略评审 | T5.1/T5.5 |
| 16 | 升级耗时长导致体验差 | 擦除慢 + 波特率低 + 双份镜像 | 用户以为死机，中途断电 | 中 | UI 明确进度与「请勿断电」；握手后升速；实测后优化（A3 减包） | T5.6/T8.4 |

## 断电注入测试矩阵（T7.2）

每条：断电 -> 上电 -> 期望结果 -> 再发起一次升级应成功。

| # | 断电点 | 期望 |
|---|---|---|
| 1 | 收包中途（QSPI 写入中） | 启动旧版本；再次升级能从记录的偏移续传或重传 |
| 2 | 整包校验中 | 启动旧版本；stage 状态仍是 RECEIVING/COMPLETE，不误判为已校验 |
| 3 | 写 CM7 非活动槽中途 | 启动旧版本；该槽被标记为未知，下次写入前先擦干净 |
| 4 | 写 CM7 槽完成后、写元数据之前 | 启动旧版本；新槽内容存在但不被采用（元数据未变） |
| 5 | 写元数据记录中途（造坏 word） | BL 跳过坏记录，取上一条有效状态，启动旧版本 |
| 6 | BL 校验新槽并切换后、应用确认之前 | 试用计数生效；再断电若干次后回滚到旧版本 |
| 7 | 应用已确认、正常运行时 | 启动新版本 |
| 8 | 写 CM4 槽 B（备份）中途 | CM4 继续跑旧版本；备份状态标记为无效，下次重建 |
| 9 | 写 CM4 槽 A 中途 | BL 检测 `m4_state` 非 CLEAN，从 B 恢复 A；CM4 回到旧版本 |
| 10 | CM4 复位后、确认前 | 超时后自动从 B 恢复 A（或重启重试后成功） |
| 11 | 元数据换代（擦另一半区）中途 | 另一半区仍有完整状态，正常启动 |
| 12 | 救援模式收包中途 | 重新上电仍进救援模式，可从偏移续传 |
